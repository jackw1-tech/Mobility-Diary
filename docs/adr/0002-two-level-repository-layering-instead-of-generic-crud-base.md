# Drop the generic CRUD base classes; the mobile app layers repositories in two levels, not three

The Flutter app was scaffolded from the jackw1-tech Pine boilerplate, which ships three unused scaffolding files: `lib/repositories/base_repository.dart` (`BaseRepository<T>` with `getAll/get/create/update/delete`), `lib/network/service/base_service.dart` (`BaseService` with the same five operations over `Map<String, dynamic>`, keyed by a `tableName`), and `lib/network/service/impl/base_service_impl.dart` (six lines, entirely commented out — a Mason scaffold never filled in). The implied pattern is three levels: a generic `Base<X>` contract, a per-feature abstract contract extending it, and a per-feature implementation.

No feature ever adopted it. All ten features (Auth, Trips, TripTrack, Acquisition, Analytics, Places, PrivacySettings, TripPrivacyExport, RouteAssistant, CurrentLocation) use two levels instead: an abstract `FooRepository` declaring domain-specific methods, and a `FooRepositoryImpl implements FooRepository`. We decided to delete the three dead files and treat the two-level shape as the project's convention.

The generic base doesn't fit this domain. The five CRUD operations assume a resource collection addressed by string id, and most repositories here aren't shaped that way: `AuthRepository` exposes `login`/`logout`/`restoreSession`/`accessToken`; `AcquisitionRepository` exposes `startTracking`/`stopTracking`/`ingestEvent`/`resumeSync`; `RouteAssistantRepository` computes a route between two points. Forcing them through `getAll/get/create/update/delete` would mean either implementing methods that throw `UnimplementedError`, or keeping a second pattern alongside the first — in which case the base class buys nothing. `BaseService` is a worse fit still: it returns raw `Map<String, dynamic>`, which would put untyped wire data where Pine expects a DTO, and its `tableName` getter assumes a uniform REST resource layout the backend doesn't have (endpoints are grouped by bounded context, not by table).

This is a decision about the *shape* of the layering, not about Pine's rules. The layer separation Pine actually asks for — UI reads state from a Cubit, Cubit talks to a Repository, Repository talks to a Service and converts DTOs through a Mapper, no layer reaching past its neighbour — is already respected across all ten features and is unaffected by this change.

## Considered and rejected

- **Retrofit all ten repositories onto `BaseRepository<T>`.** The cost lands entirely on the repositories that are least CRUD-shaped, and the benefit is a shared supertype nothing consumes: no code anywhere takes a `BaseRepository<T>` as a parameter or iterates over repositories generically. It would be type hierarchy for its own sake.
- **Keep the files as documentation of the intended pattern.** Dead code doesn't document intent, it obscures it — a reader finding `BaseRepository<T>` reasonably assumes some feature uses it, and has to grep to discover none does. That is the same cost the files impose today.
- **Introduce a narrower shared base** (e.g. a `ReadOnlyRepository<T>` for the genuinely list-shaped features: Trips, Places, Analytics). Plausible, but premature: those three don't currently share behaviour beyond returning `AppResult<List<T>>`, which is already a shared type. Worth revisiting only if concrete duplication appears between them.
- **Adopt Pine's formal `DTOMapper<D, M>` contract at the same time.** Related but separate: no mapper in the project implements the package's `DTOMapper`/`DTO` interfaces, using ad-hoc per-feature mapper classes instead. Conforming would mean splitting each per-feature mapper (e.g. `TripsMapper`, nine methods over six DTO/model pairs) into one class per pair. Left as an open question, deliberately not bundled into this decision.
