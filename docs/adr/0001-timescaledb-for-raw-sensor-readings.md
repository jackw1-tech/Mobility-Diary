# Add a TimescaleDB hypertable for raw sensor readings, alongside object storage

The course specification for this project (CAS_2026-4.pdf, Proposal 2 — *Privacy-Aware Mobility Diary with HAR*) recommends a dedicated database for temporal/sequential data, separate from the PostGIS store used for spatial data. The original design didn't satisfy this: raw accelerometer/gyroscope windows were only ever staged through S3-compatible object storage (presign-confirm-complete upload) and discarded after HAR inference, leaving no queryable record of raw sensor readings — needed, among other things, to build a labelled evaluation set for the still-outstanding HAR accuracy/precision/recall/confusion-matrix metrics.

We decided to add TimescaleDB as an extension on the *same* PostgreSQL instance already running PostGIS (swap the `db` image in `back-end/infra/docker-compose.yml` for one bundling both, e.g. `timescale/timescaledb-postgis`), rather than a separate database service. This keeps `trip_id` a real foreign key to `Trip` and avoids a second system to keep in sync. The object-storage upload pipeline is left untouched — it remains the durable, replayable source of truth. The hypertable is a purely additive, queryable projection, populated by a `bulk_create` step (batched) inside the existing Celery HAR task, immediately after MDHARW1 decoding and before normalization — so it stores the real physical sensor values, not the network's normalized input. Schema is wide-format: one row per sample instant, keyed by `(trip_id, timestamp)`, with six columns (`accel_x/y/z`, `gyro_x/y/z`).

This follows the standard **feature-store dual-write pattern**: decode once, then fan the same data out to two destinations in parallel — the in-memory array feeds CNN+GRU inference immediately (the "online" path), and the same values are also persisted to TimescaleDB (the "offline" path) for later querying, evaluation, and reprocessing. The HAR task never reads back what it just wrote; only other, later consumers (the evaluation script, a future manual reprocessing run) query TimescaleDB.

## Considered and rejected

- **Route raw bytes through a Django endpoint instead of object storage.** Would reintroduce large binary payloads into the synchronous web process — exactly what the presign-confirm-complete protocol was built to avoid.
- **`django-timescaledb` package** for hypertable creation. Rejected in favor of a one-line `RunSQL("SELECT create_hypertable(...)")` migration step — fewer dependencies to understand and defend for the marginal convenience gained.
- **Raw `COPY` instead of `bulk_create`.** `COPY` is faster but bypasses the ORM entirely. The insert runs inside an already-asynchronous Celery task, so the extra throughput isn't needed at this project's scale, and `bulk_create` keeps the code in plain Django.
- **Retiring the object-storage blobs** once the hypertable exists. Rejected: the blobs are the only way to fully reprocess a trip from scratch (e.g. after a decoding bug fix or a schema change), the same replay principle the system already applies to trips via `source_trip_id`.
- **Splitting into two Celery tasks** (`materialize_raw_sensor_readings` then `run_har_inference`, the second reading its input from TimescaleDB instead of the in-memory decoded array). Rejected for the default pipeline: querying back data the task just wrote is strictly more I/O than using the array already in memory, and is the opposite of the feature-store pattern (compute once, fan out the write, don't round-trip through the database to consume your own output). A reusable query function (`load_trip_windows_from_db(trip_id)`) is still worth building, but only for consumers that don't already have the data in memory — e.g. the HAR evaluation script that closes the outstanding accuracy/precision/recall/confusion-matrix gap.
